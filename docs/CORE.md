# コアロジック

推薦 Worker がグラフ上で何を計算するか。HTTP の型と地点カタログの選び方は [`RECOMMENDER.md`](./RECOMMENDER.md)。並べ方の意味は [`PRODUCT.md`](./PRODUCT.md)。グラフの中身は [`DATA.md`](./DATA.md)。

ここは計算の手順と向きだけを決める。`apps/worker/src/recommend.ts` と `graph.ts` の正本。

## 一本の経路

構内グラフで出すのは次だけ。

```text
各自の改札（または confirmed） → 集合場所 → 出口
```

出口から目的地はグラフの外にある。距離は出さず、出口を `origin` にした Google Maps の徒歩 URL を返す。

計算しない。

- 改札から目的地までの一本の経路
- 集合場所から目的地までの構内経路（出口を経由しないもの）
- 座標から合成した集合点
- 目的地の座標が集合場所を幾何的に引っ張ること

集合場所はカタログに載っている名前付き地点から選ぶ。利用者が歩く経路は、合流前が改札→集合場所、合流後が集合場所→出口。

## 先に一点を決めてから採点しない

集合場所を先に決めて、あとからルートを足すのではない。全集合候補について、参加者の負担と出口方向を採点してから並べる。出口方向は順位の 4 段目（同点のときだけ）に効く。

## 手順

1. 各参加者の始点集合を決める。
2. 順方向の隣接で、参加者ごとに多点始点最短を 1 回ずつ取る。これが改札→集合候補。
3. 逆方向の隣接で、全出口を始点にした多点始点最短を 1 回取る。これが集合場所→出口。
4. 各集合候補を採点する。届かない候補は `infeasible`。
5. [`PRODUCT.md`](./PRODUCT.md) の順で並べ、選ばれた経路を復元する。

2 と 3 は互いに独立なので、どちらを先に走らせても結果は変わらない。候補ごとに探索を回さない。

## 始点

次の順。

1. `confirmed` があればそのノード 1 点。
2. `entry` が改札（`CatalogRef` / `NodeRef`）ならそのノード 1 点。
3. `entry` が路線（`LineRef`）なら、その路線の改札すべて。

3 のとき、その人の距離は「どの改札を使っても一番短い値」になる。同じ距離なら `nodeId` の辞書順。選ばれた改札は `legs[].entry` に入れる。

## 通行可能

最短距離は通行可能な辺の `distanceM` の和。辺は次をすべて満たすときだけ使う。

1. 向きが合っている。
2. `asOf` があるとき、時間帯外の辺は使わない。
3. `step_free` のとき、`vertical` が `stairs` / `escalator` / `unknown` の辺は使わない。エレベーターは時間帯内なら使う。

## 順方向：改札 → 集合場所

リンクは取り込み時点で `from` → `to` に開いてある。順方向の隣接はこの向き。

各参加者について、始点集合から Dijkstra を 1 回走らせ、全ノードへの距離と先行辺を持つ。集合候補 `M` への距離が、その人の `legs[].distanceM` になる。`sourceId` が選ばれた改札。

経路の復元は、`M` から先行を辿って反転する。`pathNodeIds[0]` は改札、末尾は集合場所。

## 逆方向：集合場所 → 出口

意味上ほしい距離は、元グラフを歩いた **集合場所 → 出口**。出口ごとに順方向の探索を回すと、出口の件数ぶんになる。

同じ距離は、辺を逆にしたグラフ上で **出口 → 集合場所** の多点始点最短が出す。逆方向の隣接は、各リンクについて `to` → `from` を張る。リンク ID は元のまま。通行可能性も元のリンクを見る。

出口 `E` の持ち出しコストは次。定数の意味は [`RECOMMENDER.md`](./RECOMMENDER.md) の出口の選び方。

```
haversine(E, 目的地) × 1.35
  ＋ 看板の文字が無ければ 60m
```

これを始点の初期コストにして、全出口から逆隣接で Dijkstra を 1 回走らせる。集合候補 `M` に届いたときの `sourceId` が選ばれた出口。届いた距離から持ち出しコストを引いた値が、実際に歩く `onward.distanceM`。

経路の復元は、逆探索の先行を `M` から辿ると出口始まりになる。もう一度反転して、`pathNodeIds[0]` を集合場所、末尾を出口にする。リンク ID の列も同じ向きに反転する。

**順方向の隣接で出口から探索してはならない。** それは出口→集合場所の徒歩であり、片方向の辺では集合場所→出口と一致しない。実データには双方向化されていない有向辺がある。固定 fixture は往路と復路を両方置いているので、この違いを検出しない。

片方向の例。集合場所 `M` から出口 `E` へだけ辺があるとき、正しい探索は `M` → `E` を採用する。出口から順方向に探索すると `E` → `M` が無く、別の出口を選ぶか、候補を落とす。

## 採点

各集合候補について。

| 値 | 中身 |
|---|---|
| `maxDistanceM` | 各人の改札→集合場所のうち最大 |
| `sumDistanceM` | その和 |
| `onwardDistanceM` | 集合場所→選ばれた出口の徒歩。地上の見積もりは含めない |
| `explainability` | カタログの整数。学習しない |

どれかの参加者が `M` に届かない、またはどの出口からも `M` へ（逆隣接で）届かないときは `infeasible`。制約を外すと届くなら原因は `step_free` または `hours`、そうでなければグラフの欠け。全員がどの集合候補にも届かないときは `disconnected`。

並べ方は [`PRODUCT.md`](./PRODUCT.md) の順。同点だけ次へ進む。

1. 全員が候補へ届き、必須のアクセシビリティを満たす。
2. `maxDistanceM` が最小。
3. `sumDistanceM` が最小。
4. `onwardDistanceM` が最小。
5. `explainability` が大きい。

それでも同点なら `nodeId` の辞書順。同じ入力なら同じ順位。

目的地の座標が効くのは出口の持ち出しコストだけである。その結果選ばれた出口への構内距離が、4 段目に入る。1〜3 段目（改札→集合場所）には使わない。

`reasons` は実際に効いた段だけを入れる。最大負担で一位が決まったら `minimax` を入れ、合計は入れない。段差なし指定があるときだけ `step_free` を入れる。文言はコードから組み立てる。

歩行速度 `1.2` m/s は表示用の秒数だけに使う。順位のキーにしない。

## テスト

契約のゴールデンは [`RECOMMENDER.md`](./RECOMMENDER.md) のテストに従う。向きについては次を足す。

- 片方向の辺だけがある小さなグラフで、集合場所→出口は通れて出口→集合場所は通れないとき、`onward.pathNodeIds` はその辺を使う。逆向きだけの辺は使わない。
- `onward.pathNodeIds[0]` は集合場所、末尾は出口。
- 目的地の座標を変えると出口が変わりうる。各人の `legs[].distanceM` は変わらない。
