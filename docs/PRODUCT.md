# プロダクト方針

## 解く問題

巨大駅では「新宿駅で待ち合わせ」だけでは不十分です。異なる鉄道会社・路線・階から来る人は、同じ出口名を別の場所として理解したり、階や通路を誤ったりします。また、最短距離だけで集合地点を選ぶと、一人だけが複雑な通路を歩かされることがあります。

あつまっぷは、各参加者の到着経路と集合後の目的地を使い、次を満たす集合地点と経路を提案するモバイルWebです。

- 全員の移動負担が偏りすぎない。
- 名前と見た目で説明できるランドマークである。
- 階移動や分岐が少なく、迷いにくい。
- 集合後、全員で地上へ出るまでが短い。

## 最初の対象

JR・京王線・東京メトロ丸ノ内線で来る3人が新宿駅西側で集合し、東京都庁へ向かうケースを作ります。集合場所は駅の構内・周辺の地点です。都庁は集合したあとに向かう目的地であり、集合場所にはしません。

## 利用体験

1. ホストが名前、行き先、使える期限を入れてルームを作り、招待リンクを配る。
2. 招待された人はリンクを開き、名前を入れ、何を共有するかを読んで同意する。
3. 各自が到着路線を一覧から選ぶ。乗換案内の画面から読み取ると、同じ欄に入る。読み取った内容は画面で確かめてから確定する。
4. 誰かが入るたび、到着情報が変わるたびに候補を作り直す。ホストが候補を比べて集合場所を決める。参加者も同じ候補を見られる。
5. 共有ルームで、各参加者の到着状態と申告を見る。
6. 各自が自分の経路を1手順ずつ進む。迷った時は、手動選択または目の前の案内板から経路上の候補へ戻る。
7. 合流後は全員で出口まで進む。出口に着いたら、出口を出発地・目的地を到着地にした Google Maps の徒歩経路を開く。

アカウントは作りません。参加はリンクと名前だけです。

共有するのは出発地そのものではなく、案内に必要な到着駅と路線、そして本人が申告した到着見込みです。改札は路線から選ぶので、利用者は選びません。招待の承認と共有の同意は同じ意味にせず、画面上で分けます。

## 集合地点の評価

候補は改札前、地上の大きな口（西口前、東南口など）、バスタ前、タクシー乗り場、名前のある店、交番や案内所、固有名のある建物入口のように、口頭で場所が伝わる地点だけにする。店名は国交省の屋内地図の表記を使う。番号だけの出口（「7」「A16」）は集合場所にはせず、集合したあと地上へ出るときに使う。

MVPは説明できない合成点ではなく、次の順で候補を並べます。

1. 通行可能性と必須のアクセシビリティ条件を満たす。
2. 全員のうち最大の移動コストを最小化する。
3. 同点なら全員の合計移動コストを最小化する。
4. さらに同点なら、集合場所から出口までが短い地点を選ぶ。
5. 最後にランドマークの固有性と説明しやすさで比較する。

画面には各参加者の所要時間、階移動、分岐、バリアフリー条件と推薦理由を表示します。将来重みを導入する場合も、現地テスト前に正解として固定しません。

## 経路の手順

画面に出すのは、歩行網の全点ではなく、次の区切りだけです。

- 名前のある地点（改札、集合場所、出口、その他の名前付き）
- 実際に曲がる場所
- 階が変わる場所（階段・エスカレーター・エレベーターの両端）

次数では区切りません。設備への行き止まりが多く、直進の手順が並びます。

経路画面に構内の地図を出す。B3〜2F を1つずつ切り替える。地下は Shapefile の面、1F は地理院地図の上に地上の地物を重ねる。2F は屋内の面を残し、甲州街道側の屋外だけ地理院地図を見せる。3F・4F は見ない。経路の計算は同じ配布の歩行網です。

## 提出までの縦切り

最初に完成させる一本。

```text
ホストが名前・行き先・期限を入れてルームを作り、招待リンクを配る
  -> 招待された人がリンクを開き、名前を入れ、共有範囲に同意する
  -> 各自が到着路線を選ぶ（乗換案内の画面から読み取ってもよい）
  -> オープンデータの経路グラフから集合候補を比較する。人が増えるたび作り直す
  -> ホストが集合場所を決める
  -> 集合場所まで各自の経路を1手順ずつ表示する
  -> 二端末で到着状態と申告を共有する
  -> 手動ランドマーク確認で経路へ戻る
  -> 合流後、全員で出口まで進み、出口から目的地へ Google Maps を開く
```

提出できる公開 Web を先に完成させ、WASM・OCR・Live AI・3D は縦切りを壊さず足す。

API と画面は分けて進める。画面と部品は Figma。課題は [Linear の TOK](https://linear.app/hirotofurugen/team/TOK/overview) で管理する。

## 差別化

既存の駅ナビが一人を目的地へ案内するのに対し、本企画は次を中心価値にします。

- 複数人が一地点へ収束する経路
- 一人へ負担を集中させない公平性
- 集合後、全員で地上へ出るところまで含む地点選定
- 共有ルームによる到着状況の同期
- GPSを過信せず、案内板と経路データで現在地を再確認
- AIの推測と、公式グラフに基づく経路決定の分離

## MVP

### 必須

- 到着した路線を一覧から選ぶと、その路線の改札から集合地点までの経路を計算できる。改札は利用者に選ばせない。一覧には、取り込んだ改札がある路線をすべて出す（実データでは JR・京王・丸ノ内・小田急・大江戸・都営新宿・西武新宿）。代表ケースは最初の 3 つだが、載っていない路線の人が参加できなくなるので絞らない。
- 新宿駅の周辺から行き先を選べる。出口は「集合場所からの徒歩＋出口から行き先までの見積もり」が最短のものを使う。看板の文字はそのまま出す。
- 国交省の屋内地図から作った経路グラフで、集合地点までの経路を計算できる。東京都の店名は使わない。
- 集合地点と推薦理由を日本語で説明できる。各参加者の所要時間、階移動、分岐、その地点の設備を出す。
- 共有ルームで参加者の状態と確認済みノードを同期できる。
- 改札、階、ランドマークを手動確認できる。
- 公開URLをスマートフォンから利用できる。
- PWAで使用できる。

### 検証機能

- OCR／Visionで案内板から近傍候補を絞る。
- Live AIが音声で撮影を助け、候補制約された地点確認を行う。
- 現地でランドマーク候補と経路の正しさを確認する。

### MVP後

- LOD4の3D構内表示
- Google Maps Routes APIによる任意目的地の出口比較
- 長時間または連続的なLive AI案内

## 成功条件

- 代表3経路で、利用者が集合地点と理由を理解できる。
- 各分岐に手動または画像による復帰手段がある。
- Visionが不明な時に棄権し、誤った地点を自動確定しない。
- 初見のメンバーが説明なしでも共有ルームへ参加できる。
- 招待参加者が確認済みの移動予定を再入力せず、共有範囲を理解して参加できる。
- デモがオープンデータ（国交省の屋内地図）の具体的な価値を示す。
